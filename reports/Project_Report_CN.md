# Sense When Needed：事件驱动的自适应多传感器活动理解系统

**课程项目报告** — 数据：WISDM 智能手表数据集（UCI ML Repository, id 507）+ 自采手机录音数据（Sensor Logger）

---

## 1. 问题与动机（Problem and Motivation）

传统的普适感知系统让每一个传感器不停地采样、每一个模型不停地运行，完全不管这些信息此刻是否真的被需要。一个以 20 Hz 流式运行的 IMU、每秒轮询一次的 GPS、对每个时间窗口都调用一次的大语言模型，把它们绝大部分的电量和 token 都浪费在了**冗余的分钟**上——用户已经静坐了半小时，什么都没有变化。

本项目回答原方案中提出的机器学习问题：

> **系统能否利用低成本传感器来判断"何时需要更多信息"，并据此动态启用昂贵传感器（GPS）和 LLM 调用，在保持活动识别能力的同时大幅降低资源消耗？**

这个问题之所以重要，有三个原因：

1. **这是一个决策问题，而不是分类问题。** 核心挑战不在识别活动本身（这已基本被解决），而在于*为信息估值*：什么时候一个新样本值得为其改变决策而付费？
2. **真实传感器数据流让权衡变得可量化。** 我们可以精确计算每一分占空比能换来多少识别精度，以及"每个窗口都调 LLM（3584 次/小时）"与"只在确认的状态转换时调（10.8 次/小时）"在用户可感知层面是否有任何区别。
3. **落地部署才是最有意思的部分。** 在实验室数据集（WISDM 腕表）上训练的模型，遇到装在口袋里的真手机时面对的是另一个分布。本项目因此完成了从仿真回放，到可运行的 iOS App，再到端上个性化模型的完整闭环——而我们发现的失败模式（如 walking 与 stairs 的混淆）本身就是有价值的信息。

**一句话结果**：事件驱动策略用 **24.2% 的 IMU 占空比**复现了常开式系统的识别精度（0.798 vs. 0.801，IMU 能耗降低 3.9 倍，0.94 vs. 3.67 J/h），只在真实活动转换时调用 LLM（10.8 次/小时），GPS 每小时仅开启 16 秒——事件检测 F1 0.44，触发延迟中位数 6.1 秒。

## 2. 方法与实现（Approach and Implementation）

### 2.1 系统设计

系统是一个由混合式变化点检测器驱动的三态状态机：

```
IDLE   : 每 6 秒进行一次 1 s @ 20 Hz 微突发采样（16.7% 占空比）
         └─ 低成本 1 s 窗口分类器（多数投票）维持实时活动估计
         └─ 突发统计历史（最近 4 次突发 = 24 s 上下文）
         └─ 事件检测（每 6 秒，双分支）：
              规则分支：幅值/能量的稳健 z 分数
              学习分支：随机森林 P(change) ≥ 0.5
              任一分支自信即触发（两个独立操作点）
ACTIVE : 连续 20 Hz 采样；每 3 秒提取 59 维特征窗口交给主随机森林分类；
         置信度 ≥ 0.85（或 ≥ 0.60 且连续一致）时提交标签
CONTEXT: 提交标签发生变化 → 结构化 JSON → LLM 摘要；
         检测到运动开始 → 开启 GPS 5 秒（GPS 功耗 ≈ 30× IMU）
回到 IDLE: 重建参考历史 + 8 秒冷却期（防抖动）
```

关键设计决策，每一条都由一次测量驱动（见 §3）：

- **占空比突发采样，而非字面上的 1 Hz 采样。** 原方案假设 IDLE 阶段用 1 Hz 采样；我们实测发现严重混叠——约 2 Hz 的步态信号被 1 Hz 采样后退化为相位漂移的慢调制，事件排序质量崩塌到随机水平（AP 0.033）。突发采样（20 Hz × 1 s / 6 s）以几乎相同的能耗保留了完整的步态周期信息。
- **多保真度分类。** 1 s 窗口随机森林相比 3 s 窗口只损失 1.2 个百分点的精度，因此 IDLE 阶段可以输出*可用的*估计，而不必沉默等待。
- **两个独立的检测器操作点。** 单一共享阈值会悄悄禁用其中一个分支（我们真实踩过的 bug）：规则分支提供召回率，RF 分支提供精确率；以 max(p_rf, rule) 触发且 RF ≥ 0.5、z ≥ 4.0 的配置优于任何单独分支。

### 2.2 模型

| 模型 | 输入 | 结构 | 测试精度（WISDM，受试者级划分） |
|---|---|---|---|
| 主分类器 | 3 s @ 20 Hz 加速度+陀螺仪 → 59 维特征（时域统计、幅值谱：主频/频带能量/谱熵、轴间相关） | 随机森林，300 棵树 | 0.805（macro-F1 0.801） |
| 低成本分类器 | 1 s @ 20 Hz | 随机森林，200 棵树 | 0.793（macro-F1 0.790） |
| 事件检测器 | (4, 6) 突发统计历史 → 稳健 z、比值、离散度 | 随机森林 300 棵树 + 规则分支 | 事件 F1 0.44（P 0.33 / R 0.67） |

### 2.3 实际完成的工作

1. **完整的 Python 代码库**（`swn/` + `scripts/`）：WISDM 数据管线（47 名受试者、94 个回放会话、698.6 分钟、139 次真实状态转换）、训练、**按采样付费的回放模拟器**（唯一能接触完整 20 Hz 录音的组件；各策略*仅仅*在"何时付费"上不同）、三策略闭环评估、消融实验、图表和交互式看板。
2. **可运行的 iOS App**（基于开源 Core Motion 采集器 fork），包含：
   - 用 Swift 实现的完整 SWN 模块：与 Python 管线数值一致的特征提取（已交叉验证）、Core ML 推理，以及在专用 20 Hz `DeviceMotion` 流上运行同样的三态策略；
   - **生活日记**：拍照 + "记录此刻"条目，本地持久化，时间戳与传感器 CSV 对齐；
   - **LLM 周报**：最近 7 天日记 + 活动时间线 → 生活方式总结与健康建议，通过任意 OpenAI 兼容 API 调用（用户自带 key）；
   - 活动变化会**自动写入日记**，周报因此免费获得活动时间线。
3. **真机数据采集**：用 Sensor Logger（100 Hz 运动导出）采集，配合离线管线（`process_recording.py`）完成单位换算（g → m/s²）、重采样到 20 Hz，并在任意录音上回放*同一套*策略。
4. **个性化管线**（`personalize.py`）：在 WISDM 训练受试者 + 带真值标注的个人窗口上重训全部三个模型，并在未触碰的 WISDM 测试受试者上做显式的无回退检查。

## 3. 实验结果（Experimental Results）

### 3.1 主对比实验（10 名留出受试者，约 2.4 小时闭环回放）

| 指标 | 常开式 | 周期式 3s/10s | **事件驱动（本文）** |
|---|---|---|---|
| 跟踪精度 | **0.801** | 0.789 | 0.798 |
| Macro F1 | **0.823** | 0.811 | 0.811 |
| IMU 占空比 | 100% | 29.8% | **24.2%** |
| IMU 能耗代理（J/h） | 3.67 | 1.15 | **0.94**（↓3.9 倍） |
| 含 GPS 总能耗（J/h） | 3.67 | 1.15 | 1.42（↓61%） |
| LLM 调用（次/小时） | — | — | **10.8** |
| 标签切换延迟（中位） | 3.1 s | 10.2 s | 12.1 s（vote=1 时 6.1 s） |

**结论**：事件驱动策略用 24% 的采样量买回了常开式 99.7% 的精度，且以低 19% 的采样量比周期式基线高 0.9 个百分点的精度——因为采样集中在变化发生的时刻。LLM 用量在设计上与窗口数量解耦：每小时 10.8 次有意义的、有叙事价值的转换播报，而不是成千上万次冗余调用。

### 3.2 事件检测按转换类型分解（30 次测试转换）

| 转换类型 | 数量 | 召回率 | 说明 |
|---|---|---|---|
| 静态→运动 | 8 | **1.000** | 能量阶跃非常明显 |
| 运动→运动 | 12 | 0.833 | 步态模式变化 |
| 运动→静态 | 1 | 1.000 | |
| 静态→静态（坐↔站） | 9 | **0.111** | 对腕部 IMU 物理上不可见 |

整体事件 F1 0.44（P 0.33 / R 0.67），延迟中位 6.1 s。由于 30 次转换中有 9 次是坐↔站（腕部加速度差异近乎为零，< 0.3 m/s²），0.67 的召回率已接近*可检测上界*（约 21/30 ≈ 0.70）。我们如实报告这一盲区，而不是把它藏进一个汇总数字里。

### 3.3 消融实验

- **A. IDLE 采样方式**：1 Hz 点采样 AP = 0.033（≈ 随机）vs. 1s 突发/6s AP = 0.137（≈ 基率的 8 倍）——定量刻画了促使我们改用占空比突发的混叠问题。
- **B. 投票窗（延迟–精度旋钮）**：vote=1 → 延迟 6.1 s，精度 −1.4 pp；vote=3 → 12.1 s，+1.4 pp。事件 F1 不变（检测器消费的是突发统计量而非标签）。
- **C. 检测器分支**：仅规则分支 F1 0.437（偏召回），仅 RF 分支 0.211（偏精确，漏掉大多数转换），混合 **0.444**——两个分支互补，且各自需要独立的操作点。

### 3.4 从仿真到真机：域偏移与个性化（初步结果）

我们用智能手机（Sensor Logger，100 Hz）录制了一段 259.5 秒、带真值标注的日常活动：0–35 s 静止，35–95 s 下楼梯，95–180 s 平地行走，180–259 s 静坐。直接套用 WISDM 训练的模型：

- 策略**锁死在错误标签上**：行走段 85/85 个主分类器窗口全部预测为 *stairs*，且在整个静坐段一直错下去。
- 在个人录音上 macro-F1 仅为 **0.462**。

诊断（实测而非猜测）：

1. **混淆在域偏移之前就存在。** 即使在 WISDM 自己的留出受试者上，**50.5% 的 walking 窗口（893/1770）被判为 stairs**——walking 是域内最差的类（F1 0.618）。腕部 IMU 从根本上观测不到*高度变化*，而下楼产生的步态振荡与平地行走几乎相同：在我们的录音中，下楼段与走平路段的特征几乎重合（主频 1.67 vs. 1.73 Hz；幅值 std 2.94 vs. 2.56 m/s²）。
2. **手机携带位置抹掉了残存的区分线索**，把决策边界整体推向 stairs。

**个性化修复**（WISDM 训练受试者 + 216 个带真值的个人窗口 ×5，重训全部三个模型）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 个人录音 macro-F1（3 s / 1 s 模型） | 0.462 / 0.406 | **1.000 / 1.000** |
| WISDM 测试受试者 macro-F1（无回退检查） | 0.801 | **0.827**（不降反升） |
| 事件检测器在 3 个真实转换点 | 擦边未触发（p 0.479 vs 0.50） | 全部触发，p_rf 0.98–0.99 |
| 端到端分段 vs. 真值 | 2 个分段，行走被吞掉 | **4 个分段，全部边界误差 ≤1 s**；检测器在 96 s 的下楼→行走转换处精确触发 |

这个过程中还发现并修复了一个真实的设计不一致：突发历史原本每 1 s 采样一次，而检测器是在 6 s 间隔的突发上训练的；将节奏对齐到训练分布后，检测器得以正常触发。

## 4. 现场演示（Live Demo，计划）

一切已构建完毕；课堂演示在一台装有个性化 Core ML 模型的 iPhone 上进行：

1. **真机实时演示（主方案）**：打开 App → 启用"活动识别" → 做"坐 → 走 → 上下楼 → 坐"的完整序列。卡片实时显示当前活动与置信度；状态转换触发事件检测器、立即重分类，并自动写入日记；能耗/占空比计数器展示 1s/6s 的 IDLE 节奏。
2. **日记 + 周报（第二块屏幕）**：打开 Daily Log 展示自动记录的活动条目和照片；点击星形图标生成 LLM 周报，总结一周活动时间线并给出健康建议。
3. **录屏备份（2–3 分钟）**：上述内容的屏幕录制，外加交互式回放看板（`artifacts/dashboard.html`），在 WISDM 会话上展示传感器状态机、事件概率、GPS 付费和 LLM 播报流——包括一个诚实的失败案例（一次坐→站转换约 3 分钟未被发现）。
4. **现场数据跑离线管线**：用几分钟前现场录制的音频跑 `process_recording.py`，展示带标签的时间线 HTML。

兜底方案：若场地 GPS/运动条件不佳，看板回放完全自包含；所有演示素材打包为一个 zip。

## 5. 讨论（Discussion）

**有效的部分。**

- 核心论点定量成立：**"何时采样"比"采样多少"更重要**。把 24% 的采样集中在变化时刻，复现了常开式精度，并以更低占空比超过了均匀周期采样。
- 多保真度设计（1 s 低成本 + 3 s 主分类）和按采样付费的模拟器，让每一个权衡（延迟 vs. 精度、GPS/LLM 纪律）都可测量、可调节，且有消融实验为每个旋钮背书。
- 把策略装进真实 iOS App 迫使我们保持工程上的诚实：特征一致性（与 Python 数值交叉验证）、单位换算、推理节奏，全都变成了显式的、可测试的契约。
- **个性化廉价且有效**：4 分钟带标注的自录数据把 F1 从 0.46 恢复到 1.00，*同时*没有损害 WISDM 留出集表现（0.801 → 0.827）。这是一条实用的端上适配配方。

**失败的部分。**

- 字面意义的 1 Hz IDLE 采样（混叠；改用占空比突发——一次由测量驱动的、偏离原方案的改动）。
- 单一共享检测器阈值（悄悄禁用了 RF 分支；已用独立操作点修复）。
- 分类器的跨设备迁移：WISDM 腕表模型在口袋里的手机上锁死在错误标签。更根本地，**walking 与 stairs 对纯 IMU 几乎不可分**——域内就有 50% 混淆，因为高度变化根本不在信号里。

**可以改进的部分。**

1. **加入气压计 / GNSS 垂直速度**作为*按需购买*的模态：几秒内几米的高度变化是最强的上下楼线索，这与项目论点完美契合——系统应当在 IMU 不确定性高时（例如步态特征含糊的运动触发之后）才购买昂贵传感器。
2. **为跨设备使用简化标签体系**（walking/stairs → locomotion 粗类），在细粒度精度不可行动时换取可靠性。
3. **更多个性化数据与受试者**：目前的个性化是单受试者、单会话、in-sample；采用留一会话（leave-one-session-out）协议并补录几段数据能让结论更严谨。
4. **静态→静态检测**需要非 IMU 模态（气压、视觉或手表姿态）——检测器的量化盲区（召回 0.111）恰好论证了本项目倡导的多模态、按需付费的扩展方向。
5. **真机实测能耗**（Energy Gauge）替代功耗模型代理。

**交付物。** 完整代码（`swn/`、`scripts/`）、训练 + 个性化模型、全部结果 JSON、图表、交互式看板、含 SWN 模块的 iOS App，以及离线/个性化管线——已打包可复现；随机种子与受试者划分均已固定并记录在案。
